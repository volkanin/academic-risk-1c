# Доработки HTTP-сервисов 1С:Университет для сервиса раннего предупреждения

**Назначение документа.** Постановка доработок слоя интеграции между 1С:Университет и ML-сервисом раннего предупреждения об академическом риске. Документ дополняет и уточняет базовую постановку TZ_http_servisy_1C_University.md (первый черновик, сохраняет силу: архитектурные принципы, срез на дату, безопасность, производительность, приёмка). Здесь зафиксировано то, что стало известно после реализации приёмной стороны: точные контракты витрин, поток событий для Kafka и выгрузка соответствия студентов с зачётными книжками.

**Статус приёмной стороны.** Внешний сервис реализован и работает: слои PostgreSQL (raw, cleaned, features, enriched), Feature Store (offline SQL-функции со срезом на дату, online Redis), модель с загрузчиком, Moodle-интеграция через веб-службы СЭО (полный обход 1568 курсов выполнен), поток событий успеваемости и оплат через Kafka (FR-7) проверен на демонстрационном контуре. Данные 1С сейчас демонстрируются синтетическим контингентом с той же структурой витрин; настоящие доработки заменяют синтетику реальными данными.

## 3. Доработка: поток событий успеваемости и оплат

Приёмная сторона уже потребляет события через Kafka (FR-7): группа потребителей фиксирует смещение после записи в хранилище, дедупликация по event_id. От 1С требуется выгрузка новых событий в контракт ниже.

### 3.1 Метод

GET /events: поток новых записей оценок, задолженностей и оплат.

Параметры: modifiedSince (обязателен для инкрементального режима, по дате внесения записи), dateFrom, dateTo (по дате события), cursor, limit. Ответ: единая оболочка базовой постановки (data, meta, errors).

### 3.2 Контракт события

| Поле | Тип | Содержание |
|---|---|---|
| event_id | строка | стабильный идентификатор события: производный от записи источника (например, UUID документа или строка вида <тип>:<UUID записи>:<номер попытки>), НЕ меняется при повторной выгрузке |
| kind | строка | grade, debt_open, debt_closed, payment |
| student_id | uuid | студент |
| occurred_at | дата | дата события: для grade дата контроля, для debt_open дата возникновения, для debt_closed дата закрытия, для payment дата оплаты или начисления |
| payload | объект | для grade: discipline_id, grade, semester; для debt_open и debt_closed: discipline_id, arose_date, closed_date; для payment: amount, overdue_days, accrual_date |

Правила:
- Одна запись источника порождает одно событие. Появление задолженности и её закрытие это два события с разными kind и разными event_id.
- event_id обязателен и стабилен: повторная выгрузка того же диапазона возвращает те же идентификаторы (на этом построена дедупликация потребителя). Если события нет в выборке повторно (закрытая задолженность уже отгружена), повторная отправка не требуется, но не вредна: потребитель отбросит дубликат.
- Порядок отправки внутри партиции не важен.

### 3.3 Режимы и регламент

- Инкрементальный режим: раз в сутки в ночные часы (п. 8 базовой постановки), modifiedSince = дата последней выгрузки.
- Первичный (исторический) режим: полная выгрузка за 5-7 лет через фоновое задание базовой постановки.
- Возврат событий при отмене документа: событие с kind, обратным исходному (debt_closed для ранее открытой), а не удаление события из потока; поток дополнения только.

## 4. Доработка: соответствие студента и зачётной книжки

Приёмная сторона связывает контингент 1С с пользователями СЭО Moodle: логин Moodle равен номеру зачётной книжки (та же механика, что в обработке 1С «Синхронизация зачетных книг с Moodle»). Сейчас связь отсутствует, витрины активности наполняются только на демонстрационном контуре.

### 4.1 Метод

GET /mapping/students-books: пары студент и номер зачётной книжки.

| Поле | Тип | Содержание |
|---|---|---|
| student_id | uuid | студент |
| book_number | строка | номер зачётной книжки (равен логину Moodle, регистр не учитывается) |
| student_state | строка | текущее состояние из СостояниеСтудентов: «Является студентом», «Задолжник» (ссылочное поле, пригодное для фильтрации выгрузки активности) |

Параметры: modifiedSince, cursor, limit.

### 4.2 Требования к обращению с данными

- book_number относится к персональным данным: передача только по защищённому каналу (HTTPS в пределах внутреннего сегмента, как в базовой постановке); в журнал регистрации пишется количество записей, не значения; в логах внешнего сервиса значения не сохраняются: при приёме заменяется хешом с солью приёмной стороны.
- Частота: после каждой регламентной синхронизации зачётных книг и не реже раза в сутки.
- Отчисленные студенты сохраняются в парах (их Moodle-активность используется в исторических данных), состояние позволяет внешнему сервису отфильтровать действующих.

## 5. Дата внесения записи (entered_at)

Требование среза на дату базовой постановки (п. 6) усиливается: каждая фактическая витрина содержит entered_at как обязательное поле. Если в источнике даты внесения нет, это фиксируется в metadata-mapping.md как ограничение и применяется компенсирующая мера asOfLag из базовой постановки; для потока событий в этом случае modifiedSince отсчитывается по дате события с запасом asOfLag.

## 6. Приёмка доработок (дополнительно к базовой постановке)

| N | Проверка | Критерий |
|---|---|---|
| 1 | Замена источника данных | Загрузка витрин через HTTP-сервис даёт в хранилище внешнего сервиса структуры, идентичные текущей загрузке файлов (перечень полей п. 2), на контрольной выборке: число записей и контрольные суммы по полям совпадают |
| 2 | Стабильность event_id | Повторная выгрузка того же диапазона /events возвращает те же идентификаторы; потребитель не увеличивает счётчики студентов |
| 3 | Поток к Kafka | События из /events, опубликованные во внешнем потоке, без потерь доходят до online-хранилища; повторная выгрузка того же диапазона не дублирует счётчики |
| 4 | Соответствие с СЭО | Доля пар, чей book_number совпадает с логином Moodle, измерена и зафиксирована (ожидание заказчика: около 100% действующих студентов) |
| 5 | Срез на дату | Приёмочная проверка базовой постановки (п. 6) на реальных данных |

## 8. Ограничения, без которых работы не начинаются

- Реализация только в расширении; типовая конфигурация не изменяется (базовая постановка, п. 2).
- Разработка и отладка на тестовой копии; рабочая база только на чтение в непиковые часы (п. 8 ТЗ).
- Персональные данные: ФИО, паспорта, адреса, контакты не выгружаются; связь по UUID; book_number только по защищённому каналу и не в логи (NFR-2, п. 9 ТЗ).
- Обращения к метаданным типовой конфигурации сосредоточены в модуле-адаптере (базовая постановка, п. 4).
