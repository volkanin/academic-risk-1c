# Требования к сервису раннего предупреждения об академическом риске студентов

Версия 1.0 (черновик), 2026-11-20.
Автор: Леонид Волканин.

## 1. Бизнес-задача

Значительная часть отчислений связана с академической задолженностью и проблемами оплаты, которые видны в учётных данных вуза за месяцы до приказа. Сегодня эти данные используются постфактум, для отчётности. Задача проекта: еженедельно формировать кураторам и сотрудникам деканата список студентов с повышенным риском отчисления в предстоящем семестре, с объяснением причин, и возвращать рассчитанные оценки в 1С:Университет.

Сервис подсказывает и приоритизирует. Решение и работа со студентом остаются за сотрудником.

## 2. Пользователи и сценарии

| Пользователь | Сценарий |
|---|---|
| Куратор | раз в неделю открывает список риска по своим группам, смотрит карточку студента с главными факторами риска, помечает отработанные случаи |
| Сотрудник деканата | видит сводку по факультетам и курсам, динамику от недели к неделе |
| Информационная система 1С | получает рассчитанные оценки по HTTP и хранит их в регистре оценок риска |

## 3. Бизнес-метрики успеха

| Метрика | Целевое значение | Обоснование |
|---|---|---|
| Recall@100 | не ниже 0.60 | при пропускной способности кураторов порядка 100 студентов в месяц список должен покрывать большинство предотвратимых отчислений; при более низком значении сервис не даёт прироста против текущей практики |
| Precision@100 | не ниже 0.30 | при доле ложных тревог выше 70% сотрудники перестают доверять списку; правило-референс «две и более задолженности» даёт существенно более низкое значение |
| Запас времени до приказа | медиана не менее 3 недель | сигнал должен приходить, пока возможна содержательная работа со студентом |

Обозначения: Recall@100, доля фактических отчислений среди первых 100 позиций упорядоченного списка; Precision@100, доля студентов с действительным риском среди тех же позиций.

Пороги закреплены до первого прогона на данных. После прогона допускается одна корректировка с обоснованием в отчёте; повторные корректировки под результат запрещены.

## 4. ML-метрики

| Метрика | Определение | Целевое значение | Обоснование |
|---|---|---|---|
| PR-AUC | площадь под кривой точность-полнота | не ниже 0.40 при доле положительного класса 10-30% (случайное значение равно доле класса) | главная метрика сравнения алгоритмов при дисбалансе классов |
| Рабочая точка recall/FPR | полнота и доля ложных срабатываний на выбранном пороге | recall не ниже 0.85 при FPR не выше 0.15 | пропуск студента в зоне риска дороже ложной тревоги; ориентир из бизнес-требований аттестации (вариант Г); порог подбирается на валидационной когорте |
| Калибровка | ECE и Brier score вероятностей | ECE не выше 0.05, Brier не выше 0.10 | деканату нужна вероятность события для планирования нагрузки, а не только упорядоченный балл |
| Справедливость (fairness) | разница recall между группами | не более 0.10 для пар групп по полу, форме обучения, статусу проживания | систематическое занижение риска для отдельных категорий студентов недопустимо |
| Время инференса | отклик на одного студента и на весь контингент | не более 500 мс на студента в API; пересчёт 2 000 студентов не более 10 минут в пакетном режиме | еженедельный ночной пересчёт и точечные запросы из интерфейса |

## 5. Функциональные требования

| # | Требование |
|---|---|
| FR-1 | Загрузка: открытые датасеты из файлов сохраняются в PostgreSQL (слой raw); витрины 1С (контингент, успеваемость, приказы, оплаты) поступают по HTTP и сохраняются в тот же слой |
| FR-2 | Слои данных: обязательные raw, cleaned, features и дополнительный enriched в PostgreSQL; переходы воспроизводятся ETL-скриптом |
| FR-3 | Признаки: группы демографии, входного уровня, академические, динамика, финансовые, групповой контекст; признак на дату D использует только сведения, известные на D; SQL-функции исторического заполнения по срезу на дату |
| FR-4 | Модели: базовая логистическая регрессия, минимум три дополнительных алгоритма, подбор гиперпараметров с кросс-валидацией по когортам, обоснованный выбор финальной модели |
| FR-5 | Объяснение: для каждого студента главные факторы риска (SHAP) в человекочитаемой формулировке |
| FR-6 | Feature Store: Offline-хранилище в PostgreSQL, Online-хранилище в Redis с материализацией, единый Python API чтения |
| FR-7 | Потоковая обработка: события успеваемости и оплат идут через Kafka; группа потребителей фиксирует смещение только после успешной записи в хранилище |
| FR-8 | REST API: скоринг одного студента и пакета, объяснение факторов, проверка доступности, валидация входных данных |
| FR-9 | Возврат в 1С: пакетный приём оценок с идемпотентностью (повторная отправка не создаёт дублей), с версией модели и датой расчёта |
| FR-10 | Интерфейс: список риска с фильтрами, карточка студента, сводные показатели по подразделениям, пометка отработанных случаев |
| FR-11 | Мониторинг: технические метрики API, дрейф распределений признаков (PSI), отложенная оценка качества на закрытых когортах |
| FR-12 | WebScraping: сбор открытых сведений о направлениях подготовки в слой enriched |

## 6. Нефункциональные требования

| # | Требование |
|---|---|
| NFR-1 | Воспроизводимость: docker compose поднимает весь стек одной командой; версии Python и библиотек зафиксированы; ноутбуки воспроизводят таблицу метрик |
| NFR-2 | Персональные данные: реальные данные студентов не используются; в витринах нет ФИО, паспортов, контактов; идентификация по UUID; требования к обезличиванию при переносе на реальные данные описываются в отчёте |
| NFR-3 | Безопасность интеграции: отдельный пользователь 1С с правом только чтения, HTTPS, журнал обращений без персональных данных |
| NFR-4 | Устойчивость интеграции: обращения к метаданным 1С сосредоточены в модуле-адаптере, обновление конфигурации не ломает выгрузку |
| NFR-5 | Тестируемость: покрытие unit и интеграционными тестами выше 60% |
| NFR-6 | Влияние на базу вуза: порционная выгрузка, непиковые часы, тайм-ауты (детально в ТЗ интеграционного слоя docs/TZ_1C.md) |
| NFR-7 | Наблюдаемость: журналы с идентификатором запроса, предупреждения при деградации качества |

## 7. Ограничения

- Синтетический контингент проверяет работоспособность конвейера, а не качество прогноза; главная оценка качества выполняется на открытых данных.
- Учёт посещаемости не рассматривается, в доступных источниках он отсутствует.
- Режим работы пакетный и еженедельный; решения в реальном времени за миллисекунды не требуются.
- Оценка экономического эффекта приводится как экспертная оценка, без подтверждения на реальном контингенте.
